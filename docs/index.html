The loop

What happens in one run

The model asks for a tool, the harness runs it, and the result goes back into the conversation. Every later step resends that conversation, so long outputs cost more on every step after they appear.

01
Task
A bug report and the test command that defines success.
02
Model
Muse Spark 1.3 replies with text or a tool call.
03
Tools
read_file, search_code, edit_file, run_tests, limited to the repo.
04
Optimizer
Long output is shortened. Unchanged re-reads are answered with a note.
05
Evaluator
After the agent exits, the harness resets the repo and scores the result.

Steps 02 to 04 happen inside the agent run. Step 05 runs afterwards, in evaluate.py, and the model never sees it.

Truncation

Where truncation fired

When a tool result is over 60 lines, the optimizer keeps the first 20 and last 20 lines, plus any error or failure lines from the middle. Pick a run where it fired and look at the call it applied to.

Scoring

A finished run is not a passing run

The model saying it's done doesn't count. After the agent exits, the harness restores the original repo and runs the tests on the result. A run passes only if all four checks hold.

  • Finished: the agent ended before the 15-step limit.
  • Target tests: the tests for this task pass. For task 3, a hidden test is also run.
  • Protected tests: every other test still passes, so the agent didn't break unrelated code.
  • Scope: the agent only edited files its task allows.
Results

Effects by task

Averages can hide differences, so each task is listed. Truncation fired on tr1, tr3, and tr4, and never on tr2.

tr2 goes the other way on prompt size. Its optimized average (8,223) is above baseline (7,820). One optimized run used 9,860 prompt tokens and the others averaged about 7,815. Cost on tr2 is still lower in optimized mode, but cache hits vary more between runs than prompt size does, so treat that cost difference as noisy.
System

Two halves, one run

Agent execution · agent.py

  1. Task sent as the user messageTask text and the tool list go to the model.
  2. Model returns text or tool callsMuse Spark 1.3 through the Meta Model API.
  3. Tools runLimited to the repo. Paths outside it are rejected.
  4. Optimizer handles the outputTruncation in every truncating mode. Read cache in optimized mode only.
  5. Loop repeatsStops when the model makes no tool call, or at 15 steps.

Post-run evaluation · evaluate.py

  1. Repo resetCopied fresh from the original before each run.
  2. Finished checkRead from the run record.
  3. Target and protected testsRun by the harness, not by the agent.
  4. Scope checkEdited files compared against the task's allowed list.
  5. Records writteneval_runs.jsonl, eval_logs/, results.md.
Repository

The parts

Each component, and what it does according to the code.

agent.py

The loop. Sends messages and tool definitions to Muse Spark 1.3, runs the requested tools, appends the results, and writes one record per run to runs.jsonl. The API key comes from the environment.

tools.py

read_file, edit_file (replaces exactly one match), search_code (grep over .py files), and run_tests (pytest). Every path is resolved and rejected if it lands outside the repo.

optimize.py

truncate_output keeps the first and last 20 lines of long output plus error lines from the middle. ReadCache hashes each file it returns and answers an unchanged re-read with a short note.

evaluate.py

The harness. Resets the repo, runs the agent as a subprocess, retries runs that produced no record, runs the target and protected tests, checks scope, and writes the result files.

tasks_trigger.json

The four tasks in the final experiment. Each one lists its description, target tests, and allowed files.

pricing.json

USD per million tokens for muse-spark-1.3: input $1.25, cached input $0.15, output $4.25. Output includes reasoning tokens.

eval_runs.jsonl and eval_logs/

One record per evaluated run, and the printed output of each run. The replay and truncation views read from these.

trigger_repo_original/

The test repo: four modules with deliberate failures. It is copied fresh before every run, so runs don't share state.

Limits

What this does and doesn't show

  • One model, one synthetic repo, four tasks. These results describe this suite. They say little about coding agents in general.
  • Prompt tokens are the main measure. Cost moves with cache hits, which vary between runs more than prompt size does.
  • The read cache is not proven to save money here. It fired as designed, on the one task built to force a re-read, but its effect is inside run-to-run noise.
  • Task 4 asks for the re-read. The agent is told to read the file twice. The data shows the mechanism works, not that the agent would do this on its own.
  • Traces are only as complete as the logs. The logs record each tool call and the truncation marker, but not the full text of the output that was shortened.
